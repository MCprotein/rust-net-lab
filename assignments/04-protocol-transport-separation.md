# 과제 04: 프로토콜과 전송 계층 분리

## 선수 조건

- 과제 01~03의 외부 동작이 안정적으로 재현된다.
- 현재 코드에서 네트워크 I/O와 echo 규칙이 섞인 위치를 찾을 수 있다.

## 학습 목표

- 역할과 책임을 기준으로 모듈 경계를 만든다.
- 구체적인 네트워크 타입에 대한 프로토콜 의존성을 줄인다.
- 두 번째 구현이 들어오기 전에 필요한 최소 동작 계약을 테스트로 고정한다.

## 문제

Echo 프로토콜이 `TcpStream`이라는 구체 네트워크 타입을 직접 알지 않게 만든다. 네트워크 연결 없이도 프로토콜 동작을 테스트할 수 있어야 한다.

## 제한 조건

- 먼저 과제 01~03의 동작을 테스트로 고정한다.
- 실제 변경 이유가 없는 범용 프레임워크나 거대한 trait 계층을 만들지 않는다.
- 프로토콜 모듈은 주소 binding, 연결 수락과 스레드 생성을 담당하지 않는다.
- 전송 구현은 echo 메시지의 의미를 판단하지 않는다.
- TCP와 UDP를 같은 추상화에 억지로 넣지 않는다.

## 구현 순서

1. 현재 코드의 책임을 프로토콜, 전송, 애플리케이션과 실행으로 분류한다.
2. 네트워크를 열지 않고 검증할 수 있어야 하는 규칙을 찾는다.
3. 필요한 최소 입출력 능력을 정한다.
4. 프로토콜 동작을 메모리 또는 테스트 대역으로 검증한다.
5. 기존 TCP 실행 경로를 새 경계에 연결한다.

## 완료 조건

- 프로토콜 로직에서 `TcpListener`를 사용하지 않는다.
- 네트워크 포트를 열지 않고 핵심 echo 동작을 테스트할 수 있다.
- 기존 TCP 실행 동작이 유지된다.
- 어떤 경계가 나중에 시스템 콜 구현으로 교체되는지 설명할 수 있다.
- 새 경계를 도입한 이유를 실제 테스트 또는 두 번째 구현 요구로 설명할 수 있다.

## 직접 조사할 질문

- `Read`와 `Write`가 표현하는 최소 능력은 무엇인가?
- generic, trait object와 구체 타입 중 현재 문제에 필요한 것은 무엇인가?
- 개방폐쇄원칙과 의존성 역전은 이번 구조에서 어떻게 드러나는가?
- 추상화를 너무 일찍 만들면 어떤 비용이 생기는가?
- mock 없이도 프로토콜을 테스트할 수 있는 가장 단순한 방법은 무엇인가?
